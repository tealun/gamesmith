# 合规：立项到提审

> 本文平台事实分两类：**已核实**（来自示例项目查阅官方文档或实测，附来源页面）与**待核实**。所有条目**以官方文档为准**，规则会变；动手前重新打开来源页核对「最后编辑」日期。

## 1. 立项时必须先定的三件事

| 事项 | 为什么要先定 | 做法 |
|---|---|---|
| 正式名称 | 微信小游戏**备案通过后不能改名或改主体**，否则重新备案（已核实，来源见第 6 节） | 先商标检索，再备案；工作名（尤其英文）不作正式名 |
| 商业化路线 | 决定是否需要版号/软著等资质 | 查平台对 IAA（纯广告）与虚拟支付的不同要求 |
| 网络类型（单机/联网） | 备案按此填；改为联网要走变更并可能需要 ICP 备案 | 列出全部网络行为再判定（见第 3 节） |

## 2. 名称与商标

- [ ] 第三方商标查询做初筛，保存截图到 `docs/03_compliance/evidence/`（带日期）。
- [ ] 备案前在官方商标网（中国商标网 sbj.cnipa.gov.cn）再检索一次。重点类别依游戏性质定（示例项目以第 9、41 类为主），**类别选择待核实/请咨询专业人士**。
- [ ] 避开知名品牌与已有产品名（示例：项目最初名称撞了出行品牌，立项阶段即弃用）。
- [ ] **正式名称与简称分开管理**：认证/备案/提审材料一律用正式名称；简称只用于平台「简称」字段和口头传播。
  - 已实测（示例项目，2026-11）：微信小游戏后台有「简称」字段，手机小程序列表宫格显示简称。
  - 待核实：修改正式名称是否需要重新认证或备案变更、每年可改次数。
- [ ] 名称含英文的影响：微信 IAA 游戏在「名称含英文或『软件』字样」时需要软著（已核实，见第 6 节）。纯中文名可免。

## 3. 备案类型与网络类型

判定网络类型时逐条列出代码里的网络行为：

| 行为 | 示例项目判定 |
|---|---|
| 自建请求（`wx.request`、socket、上传下载） | 有 → 联网 |
| 远程资源 / CDN 分包 | 有 → 联网，且远程域名须 https + ICP 备案（已核实） |
| 云存档、自建排行、地区排行 | 联网 |
| 平台能力：埋点上报、转发菜单、防沉迷 | 示例项目按「不算自身联网功能」判定为单机（依据备案页说明：防沉迷、广告变现不属于自身游戏功能） |
| 开放数据域好友/群排行 | **待核实**：是否算自身联网功能 |

- 游戏类型：选与玩法最贴切的分类；「备案游戏类型是否必须与账号服务类目一致」**待核实**，准备一个回退选项。
- 系统功能下拉（示例项目所见：货币、商城、兑换码、会员/VIP、道具、体力、排行榜、设置、自定义）**只选实际存在的**；每项写一段如实描述（如「货币不可购买、充值、兑换或交易」）。
- 版本加功能（如排行榜）前先核实：备案变更还是重新备案、变更期间能否运营（**待核实**）。

## 4. 上线必备项

| 项 | 要求（微信，已核实） | 实现建议 |
|---|---|---|
| 健康游戏忠告 | 游戏开始前在显著位置**全文**登载 | 启动页全文显示，计入首帧时序 |
| 适龄提示 | 后台选择 8+/12+/16+ 并审核，平台在启动页展示 | 后台操作，不用自己画 |
| 防沉迷/实名 | 不开通虚拟支付时由平台统一接入，开发者无需开发 | 不重复造 |
| 隐私 | 不处理个人信息：后台确认「承诺未处理」；使用关系链（好友/群排行）须填隐私保护指引并实现授权弹窗 | 首版尽量不处理个人信息；埋点不含可识别身份字段 |
| 诱导分享 | 禁止强制分享、分享换利益/复活、红点暗示分享、分享图文与游戏无关等 | 「复活靠广告，传播靠内容」；转发菜单不绑奖励 |

其他平台（抖音等）对应规则：**全部待核实**，按同一张表逐项查官方文档后再填。

## 5. 字体与素材授权

- **烘焙进图片的文字也算使用字体**。只用明确允许商用、嵌入与制成图片的字体（如 SIL OFL 1.1 授权的字体），许可证文件随仓库入库。
- 授权不清的字体（示例：GPL 附字体例外的字体用于商业游戏图片）列入待核实；不确定就换 OFL 字体重新烘焙。
- 做**字体子集**减小体积；烘焙脚本发现子集外的字符直接报错（见 `art-pipeline.md`）。
- 界面其余文字用系统字体时，不打包字体文件。
- 外部素材库/音效：记录来源、授权、评估结论（引入或不引入及原因）。
- **自制或程序生成的素材也要记录**：放在一份统一的授权清单里（例如 `assets/LICENSES.md`），每行写文件或目录、来源（自制 / 程序生成 / 第三方）、生成脚本路径、是否用了第三方采样、音色库或模型。没有这份清单时，上线清单的「授权记录完整」判为缺失。参考作品只借「视觉语法」，禁止照搬图标造型、角色设计、界面布局、字体、关卡与音乐。

## 7. 待核实清单的做法

合规文档末尾维护一张编号清单，规则：

1. **只增不删**：核实后在原条目后追加「→ 日期 + 谁 + 怎么核实的 + 结论」，保留历史。
2. **只有官方原文或真机实测才能转成「已核实」**，并记下页面链接、「最后一次编辑」日期或实测日期与机型。其他 AI、第三方代办机构、论坛文章的答复只当线索：可以据此去找原文，不能直接写进事实表。官方页面没写的，不等于「不需要」。
3. 每条写明**影响什么**（哪个设计/实现依赖它）和**未核实时的兜底**（代码里 try/catch 静默、功能先不上、材料用正式名称等）。
4. 待核实条目**不得作为设计依据**；设计文档引用时链接到清单编号。
5. 每个里程碑开始时过一遍，影响本里程碑的必须关闭。

示例项目留下的通用待核实项（任何新项目都应在自己平台上重查）：

- 流量主开通门槛（官方页未写，常见说法 UV 1000 等未核实）；个人主体能否开通；无版号是否影响；每用户每日观看的具体次数。已核实：官方激励视频页写明「每个用户每天可观看激励式视频广告的次数有限」，所以展示广告按钮前要先判断广告拉取是否成功，并准备没有广告时的降级方案。
- 埋点接口的事件数、字段数、频率配额；未在后台创建的事件是否被静默丢弃；上报值是否只支持整型（见平台文档）。
- 体验版人数上限、灰度发布能力。
- 横屏胶囊按钮实际位置（多机型）。
- 个人主体备案实际耗时。
- 震动强度参数在 iOS/安卓的实际效果与最低基础库版本。
- 备案游戏类型是否必须与账号服务类目一致（官方页未写）。
- 备案后新增系统功能（如排行榜）或单机改联网，是否需要更新备案（官方备案页只写了改名称、改主体需要更新）。
- 备案后新增场景、关卡等内容，使备案文字（场景、玩法、背景）和截图过时，是否需要更新备案。核实前，至少保证提审材料与当前版本一致。
- 提审图标、截图、简介的尺寸与数量。
- 引擎启动 logo 去除/自定义的申请条件与费用（示例为 Cocos，**待核实**）。
- 抖音等其他平台：以上全部。
