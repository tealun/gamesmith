# 架构：引擎无关核心 + 引擎壳 + 配置驱动

目标：玩法规则能在 Node 里单测、在浏览器里预览、在任意引擎/平台里运行；内容生产只改配置。

## 1. 分层

```
config/*.json ──校验──┐
                       ├─ sync 脚本 ─→ 引擎工程（生成副本，勿手改）
game/core/*.ts ───────┘
   ▲ 单测 game/test        ▲ 求解器 game/tools/solve
   │                        │
画面层 view（不引用引擎全局，可离线预览）
   │
引擎壳 Boot（加载、输入、循环、音频、存档、平台适配）
   │
平台适配层 IPlatform → WxPlatform / TtPlatform / WebPlatform
```

| 层 | 允许 | 禁止 |
|---|---|---|
| core | 纯计算、可种子随机数、固定步长 `step()`、事件 | 引用引擎、`wx`/`tt` 等平台全局、`Date.now()` 驱动逻辑 |
| view | 读 core 状态、决定画什么、画在哪 | 直接调用引擎 API（经由宿主接口） |
| 壳 | 资源加载、输入→core、core 事件→音效/震动/特效 | 写玩法规则 |
| 平台层 | 存储、分享、广告、埋点、震动、生命周期、安全区 | 被 core 引用 |

要点：
- **固定步长 + 种子随机**：同一种子能复现一局，用于 bug 复现、求解器、每日挑战。
- **可擦除的 TS 语法**（无 `enum`、`namespace`、参数属性），Node 可直接运行测试与工具（Node 22+ 去类型执行，版本要求以 Node 官方为准）。
- 画面层若做成「不引用引擎」，配合一个画布模拟的精灵宿主，就能在无头浏览器里预览（第 5 节）。
- 移植约定从第一天遵守：平台 API 只在平台层；玩法不依赖平台独有能力（排行仅展示，可降级）；美术源按 2 倍分辨率；存档经平台层读写，结构写进配置规范，便于将来云存档。

## 2. 配置表

- 一张表一个 JSON：玩家手感、敌人/危险、道具、场景、片段库（按场景分文件）、关卡、无尽、界面、特效、音频、埋点编码……
- 每张表带 `schema` 版本号；字段说明写在配置规范文档（`00_03`）。允许 `_doc` / `_字段` 形式的注释键。
- 「新增同类内容 = 选原型 + 填配置 + 出美术」，不写新代码。行为原型（如 冲撞/静止/俯冲/定时砸/弹出/坠落/抛物/追赶/区域/吸拉/环境）提前在架构文档列全。
- 开关也进配置：测试开关、限时活动起止时间、自动暂停阈值、震动档位……

## 3. 校验脚本（`validate_config`）

改配置后必跑；在 CI/提交前跑。错误累计后一次性列出，退出码非 0。建议检查分组：

| 组 | 例 |
|---|---|
| 结构 | 必填字段、`schema` 版本、id 唯一 |
| 引用完整性 | 片段引用的敌人/地形存在；关卡引用的片段存在；场景缺片段库/音乐/调色板即报错 |
| 取值范围 | 概率 0–1、时长 > 0、尺寸对齐网格 |
| 内容规则 | 每关新内容 ≤ 2；地面生物脚下必须是从地面立起的实心块；出口到下一面墙留足距离；奖励后方落地区无障碍 |
| 克制矩阵 | 每种伤害类型在它出现之前已有可用的克制手段 |
| 构建模板 | AppID 格式正确、横竖屏与设计一致（构建模板会覆盖产物，空值会出问题） |

每次真机问题若能用静态规则描述，就加一条校验（见 `playtest-loop.md`）。验证新规则：先让它对已知坏数据报错，再修数据到 0 错误。

骨架：`templates/tools/validate_config.py`。

## 4. 同步脚本

- 把 `game/core/*.ts`、`config/**`、共享绘制代码复制进引擎工程；副本首行写 `GENERATED … edit the original`。
- 再次同步时只删除带该头的旧文件；**保留引擎的 `.meta` 文件**（其中的 uuid 已随工程提交，删了会断引用）。
- 处理引擎打包器差异（例：Cocos 打包器不接受 `import './x.ts'` 的后缀，同步时去掉）。
- 源里已删除的配置，同步时连同 meta 一起删除。

骨架：`templates/tools/sync_to_engine.py`。

## 5. 无引擎预览工具

为什么：编辑器通常无法在云端/Linux 容器运行，AI 助手看不到画面；评审美术与界面需要稳定截图。

做法：
1. 用 esbuild 把 view 层 + core + 画布版精灵宿主打成一个 IIFE。
2. Playwright 打开页面，注入全部配置与图集，跑若干秒（机器人自动操作），按场景/界面/片段截图。
3. 收集 `pageerror` 与 console error，有错即非 0 退出。
4. 参数：`<输出目录> [ui | 片段id | shots]`；`ui` 截全部界面（按手机比例并模拟刘海与胶囊），`shots` 按清单生成提审截图。

骨架：`templates/tools/preview.mjs`（画布直绘版，演示流程）。

## 6. 测试

- 规则测试：每条玩法规则一条测试；每个真机 bug 一条回归测试（名字写清现象与日期）。
- 「机器人通关」测试：卡住时跳过（片段可过性由求解器保证），避免测试与求解器重复且脆弱。
- 源码扫描测试：拦截已知会被目标编译器搞坏的写法（如 `[...new Set()]`，见 `platform-wechat-cocos.md`）。
- 类型检查覆盖 view 代码：为引擎模块写类型桩（stub `.d.ts`），在无引擎环境也能 typecheck。

## 7. 命令表

在 `AGENTS.md` 维护一张「命令 | 作用 | 何时必跑」表，例如：

| 命令 | 何时必跑 |
|---|---|
| `python3 tools/validate_config.py` | 改任何配置后 |
| `cd game && npm test && npm run typecheck` | 改 core 或 view 后 |
| `cd game && npm run solve [-- <id>]` | 改片段、手感参数、物理后 |
| `node tools/render_sprites.js` | 改绘制代码后 |
| `node tools/preview.js <dir> [ui\|id]` | 改 view 或图集后，看截图 |
| `python3 tools/sync_to_engine.py <工程>` | 打开引擎构建前 |
| `python3 tools/make_metas.py` | 新增引擎资源后（见平台文档） |

## 示例

示例项目（横版跑酷）：`game/core` 约 1000 行（类型、配置组装、随机数、轨迹采样、出片段导演、一局完整模拟），40+ 条规则测试；Cocos 端只有加载/输入/音频/存档外壳与两个不引用 `cc` 的画面类，预览工具在云端容器生成全部评审与备案截图。
