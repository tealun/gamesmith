# 真机试玩迭代与工作流

## 1. 闭环：反馈 → 复现 → 最小修复 → 回归 → 证据

| 步骤 | 做法 | 产出 |
|---|---|---|
| 收集 | 测试者截图/录屏 + 机型；画面常驻场景与关卡名、版本号，截图即可定位 | 编号的反馈列表 |
| 复现 | 用种子、片段 id、关卡 id 在无引擎环境复现（单测、求解器单片段模式、预览工具） | 失败的测试或截图 |
| 定位根因 | 区分「症状」与「根因」：卡在加载 → 为什么等不到？加超时只是兜底 | 一句话根因 |
| 最小修复 | 只改根因相关代码；兜底（超时、屏幕报错）可作为第二层 | 提交 |
| 回归 | 每个修复配一条测试或校验规则，名字写清现象与日期 | 测试先在旧代码失败、新代码通过 |
| 证据 | 命令输出、截图、真机复测结果；更新任务状态 | 里程碑清单「证据」列 |

处理要点：
- 一轮反馈逐条回应，**修复与新建议分开**。建议类先写进设计文档（谁、何时、原话），再实现。
- 一个提交一件事，提交信息写清现象与改法（中文即可），方便日后从 git log 找证据。
- 修复后若涉及配置/片段：校验 + 求解器全量再跑。

## 2. 文档是唯一事实来源

- 开工先读文档索引，按阅读顺序找相关事实来源。
- 改玩法、配置结构、平台接入 → **同一提交里改对应文档**。
- 决策记录格式：日期 + 决策人 + 原话/理由 + 影响范围。
- 文档分层：核心（设计、架构、配置规范、搭建）→ 规格 → 任务（里程碑清单：事项 | 状态 | 证据）→ 合规 → 演进 → 审计。
- 延后事项单独一张表，每条写**触发条件**。
- 定期审计：
  - 一致性复审：文档之间互相引用是否一致；
  - 规格↔代码对照：逐条对照设计文档与代码，缺口按 P0（上线前必须）/P1（应完成）排进任务清单。

## 3. 演进台账（防止再犯）

`docs/98_evolution/evolution-ledger.md`，一行一条：

| 列 | 内容 |
|---|---|
| ID | EVO-001… |
| Trigger/Evidence | 日期 + 现象 + 出现次数 |
| Root Cause | 为什么会发生、为什么没被拦住 |
| Local Fix | 这次怎么修（附提交） |
| Systemic Action | 加了什么自动防线（测试、校验规则、脚本退出码） |
| Guard Verification | 如何证明防线有效：临时恢复旧逻辑 → 防线报错；恢复新逻辑 → 通过 |
| Closure Level | Fixed / Guarded / Institutionalized |
| Next Planning Input | 对后续规划的提示 |

记入时机：同类问题第二次出现、一次失败改变了做法、真机发现了自动检查漏掉的问题。

示例项目的台账条目（抽象后可复用的教训）：
- 图集超限只靠人读日志 → 烘焙脚本超限即失败。
- 构建模板 AppID 为空导致游客模式 → 校验脚本检查模板。
- 场景切换按里程而片段按起点，导致跨段内容不一致 → 「片段边界 = 场景边界」+ 多种子测试。
- 地面生物放到悬空平台 → 静态规则。
- 求解器只验最优路线，漏掉撞墙后的死循环 → 回归测试 + 静态距离规则 + 求解器扩展方向。

## 4. 任务管理

- 里程碑文件：目的、清单（事项 | 状态 ☐/◐/✅ | 证据）、进展记录、Done/Fail 判据。
- Fail 判据要事先写（如「无版号无法上线 → 改资质路线并重排时间线」），让失败也有预案。
- 需要决策人线下操作的事项（注册账号、后台配置、真机测量）同步到待办工具，并在文档中标注。

## 5. 分批开放与数据驱动

- 内容分批或限时开放，先积累用户，用数据（留存、片段死亡率）决定下一批。
- 上线前就写好「继续投入 / 调整再测 / 停止转向」阈值与评估样本量（示例：约 500 新增后评估）。阈值是假设，上线后按真实数据修正。
- 赛季制设想：数据达标后，每季批量新增场景；前提是场景配置化、生成器、按场景图集与分包已就绪。

## 6. 与 AI 助手协作

- `AGENTS.md`（或 `CLAUDE.md`）写协作规则与命令表，各种 AI 工具都以它为准。
- 编辑器只能本人点选的步骤，写成逐步指引；同步、校验、提交可由助手在远程环境执行。
- 预览工具让助手「看得到画面」，评审截图直接回传。
